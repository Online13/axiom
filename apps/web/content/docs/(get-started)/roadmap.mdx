## Where we are

The specification is done: every foundation, component, behavior and pattern is written down, with its API, its states and its tokens. Phase 1 turns that into code.

Every primitive of this phase now runs in code, along with tokens, theme and the six core pieces: Title and Text, the 33 atoms, the three molecules, Passcode and the five templates. All 76 entries with styling variants ship in both `stylesheet` and `unistyles`. The first 30 compositions and the first block are in, and both demo apps show them. The theme builder is public, `add --standalone` writes any entry as one theme-free file, and the CLI is typechecked and tested in CI. What is left of the phase is the Tailwind variants, `axiom fetch` and the rest of the CI.

## Phase 1: the foundation

### Styling variants

1. `stylesheet` for every item in this phase, with the behavior / style split in place. Shipped.
2. `unistyles` for all 76 entries with styling variants, compositions and block included, with matching APIs and a demo app. Shipped.
3. `tailwind` (NativeWind / Uniwind), once the split is proven on the first two.

### Standalone mode

Shipped for `stylesheet` and `unistyles`. By default a component arrives with everything it stands on: ask for Tab and you also get the theme, the tokens and the headless core it imports. That is the right default for an app built on Axiom, and the wrong one for an app that already has its own design system and wants a single component out of the catalog.

`axiom add tab --standalone` breaks that chain. It writes one self-contained file: token values resolved inline, no `useTheme`, no import outside React, React Native and the npm packages the component uses. Nothing else is added to the project. See [the CLI](/docs/cli#standalone).

The trade is explicit. A standalone component no longer follows a theme, so light / dark and any restyling are the user's job, in a file that is already theirs to edit. What Axiom still guarantees is the behavior: the touch targets, the gestures, the states, the safe areas.

The theme-free form isn't written by hand. The CLI derives it from the registry: it inlines the items the component depends on, replaces each read of the theme with the light theme's values, and keeps the registry's types for the token groups and component tokens. The registry typechecks the standalone form of every entry in both variants, so a new entry gets one for free. Entries that render through a portal (Dialog, Menu, Bottom Sheet, Toast, Snackbar) are refused for now: a portal needs a host at the root of the app.

`useOverlayBackHandler` was not in the original plan: BottomSheet, Dialog and Menu need to close on a back gesture instead of leaving the screen, so the hook ships in three versions — `react-native`, `expo-router` and `react-navigation` — and `add` picks one from the project's `package.json`.

Two core entries were added along the way. OverlayStack lets BottomSheet, Dialog and Menu know what is open on top of them, so a sheet scales down when another opens over it. Haptics is a single `haptic()` function that switches, pickers and long presses call; it does nothing until the app [connects its own library](/docs/integrations/haptics).

### Tooling

- `registry.json` <StateTag state="shipped" /> — 86 entries, compositions and block included.
- CLI <StateTag state="progress" /> — `add` and `init` are shipped. `add` resolves internal dependencies, icon source and navigation, and has a `--watch` mode; `init` picks the styling, resolves the aliases against `tsconfig.json`, copies the foundations and the headless core, installs what they need and writes `axiom.json`. `fetch` is still to write.
- Standalone mode <StateTag state="shipped" /> — `add --standalone` for 76 entries in both variants, typechecked on their own. Portal-based entries come later.
- Demo apps <StateTag state="progress" /> — done for the `stylesheet` and `unistyles` variants: one screen per primitive, in groups from Foundations to Templates, then the compositions and the block, and a light / dark switch. The NativeWind and Uniwind apps are scaffolded and fill in with the `tailwind` variant.
- Theme builder <StateTag state="shipped" /> — public at `/theme-builder`: role overrides, presets, app and component previews, a design-system view, a canvas toolbar with slide mode and a dark-mode toggle, Google Fonts, and an export an agent can apply.
- Foundations screen <StateTag state="shipped" /> — colors, typography, spacing, radius, icons, touch targets, states.
- CI <StateTag state="progress" /> — the CLI is typechecked and its test suite runs on every change to the CLI or the registry. Still to add: typecheck per variant, props parity between variants, lint, builds. The other workflow streams an iOS simulator preview.

## Phase 2: blocks

Complete sections of an app, built from primitives and compositions, once the system is stable. [Settings section](/docs/blocks/settings-section) comes first, in phase 1; then [authentication](/docs/blocks/authentication), [onboarding](/docs/blocks/onboarding), [monetization](/docs/blocks/monetization), [profile](/docs/blocks/profile) and [commerce](/docs/blocks/commerce).

## Later

- [Agent integration](/docs/agent): the CLI commands an agent needs to find, plan and verify a screen — `search`, `info`, `plan`, `doctor`, `--json` output — plus the AGENTS.md, skill and MCP entry points. Specified, not built: only `add` and `init` are available today.
- [Patterns](/docs/patterns): selection mode, search experience, async content state…
- More [hooks](/docs/hooks): hide-on-scroll, collapsible header, keyboard-aware behavior…
- CI on Android and iOS devices, screenshots, visual tests (including parity between styling variants), accessibility checks.
